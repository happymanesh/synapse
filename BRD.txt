can i use stored procedure in administration/report instead of query ? and if yes can i pass the parameters similiar to we use for mssql sp ?

Good question — and the answer depends on details of how the engine binds and wraps queryText. Let me check rather than guess:

Short answer: yes for Postgres functions, no for true CALL procedures — and parameters work, but in Postgres style rather than MSSQL style.

Two things constrain this. Your DB is PostgreSQL 16, not MSSQL, and the engine doesn't run queryText bare — it wraps it:

POST /reports/[id]/run pre-checks the row cap with SELECT COUNT(*) FROM (<queryText>) t
FORM mode wraps with SELECT * FROM (<queryText>) __owned_wrapper WHERE created_by = $n
So whatever you put in queryText has to be legal as a subquery. A RETURNS TABLE function is; CALL my_proc(...) is not — it's a statement, can't be nested in a FROM, and can't return a result set anyway (only INOUT params, as a single row).

What works
CREATE OR REPLACE FUNCTION sp_sales_report(
  p_company   text,
  p_from_date date,
  p_to_date   date
)
RETURNS TABLE (
  company_code text, sale_date date, product_name text,
  region text, quantity int, amount numeric
)
LANGUAGE sql STABLE AS $$
  SELECT company_code, sale_date, product_name, region, quantity, amount
  FROM sample_sales
  WHERE (p_company   IS NULL OR company_code = p_company)
    AND (p_from_date IS NULL OR sale_date   >= p_from_date)
    AND (p_to_date   IS NULL OR sale_date   <= p_to_date)
  ORDER BY sale_date DESC;
$$;
Then in Report Master, queryText becomes just:

SELECT * FROM sp_sales_report(:SALES_COMPANY::text, :SALES_DATE_RANGE_FROM::date, :SALES_DATE_RANGE_TO::date)
Everything else stays as-is — ReportColumn.columnKey values just have to match the function's output column names.

Parameters
MSSQL	Here
Marker	@CompanyCode	:SALES_COMPANY
Name source	you choose	must equal the filter item's componentCode
Date range	two params you define	auto-split into :CODE_FROM / :CODE_TO
Binding	sp_executesql	rewritten to $1..$n, passed as real bind params — never string-concatenated
The one gotcha: keep the ::text / ::date casts. Unset filters arrive as SQL NULL, and Postgres can't resolve which sp_sales_report overload you mean from an untyped NULL — you'd get "function is not unique" or "could not determine data type". That's the same reason the existing seeded queries write :SALES_COMPANY::text IS NULL.

If you're stuck with a real procedure, the fix is a thin wrapper: convert it to RETURNS TABLE, or have the proc write to a temp/staging table and point a wrapper function at that.

One caveat on confidence: I'm reasoning from the binding and wrapping code I read earlier this session (bindNamedParams, bindAndWrapWithOwnership, the run route's count wrapper) — I haven't actually executed a stored function through the engine end-to-end. Want me to add sp_sales_report as a working sample report and verify it properly, so you have a template to copy for real ones?

what studio should i use for postgressSQL  16 to create tables, display data, create function etc ?

For your setup — Windows, local PG 16, and coming from an MSSQL/SSMS background — I'd go with DBeaver Community.

DBeaver Community (free, dbeaver.io)
Best all-round daily driver. Strong SQL editor with autocomplete, a data grid you can filter/sort/edit inline and export straight to CSV, a visual table designer, and a DDL tab on every object so you can read and edit function bodies directly. Handles the CREATE FUNCTION ... RETURNS TABLE work from the previous question comfortably.

pgAdmin 4 — the alternative worth knowing
Almost certainly already installed; it ships with the EDB PostgreSQL Windows installer. It's the official tool and the closest thing to SSMS in shape: dedicated right-click Create → Function / Procedure dialogs with parameter grids, rather than making you hand-write the DDL. Clunkier and browser-based, but if the wizard-style function authoring is what you miss from SSMS, use this one for that specifically.

DataGrip if you already have a JetBrains subscription — genuinely the nicest of the three, but not worth buying standalone for this.

Two things to skip: Azure Data Studio (Microsoft retired it earlier this year — don't start there despite the MSSQL familiarity), and Prisma Studio. You already have Prisma Studio via npx prisma studio, but it only renders Prisma models — sample_sales won't even appear since it's a hand-created table, and it can't create tables or functions at all. It's a row browser, not a studio in the sense you mean.

Connecting: host localhost, port 5432, database sihl_synapse. Username and password are in the DATABASE_URL line of C:\Projects\Synapse\.env.

One more thing worth fixing while you're at it: psql isn't on your PATH — I hit that earlier and had to fall back to prisma db execute. It's at C:\Program Files\PostgreSQL\16\bin. Adding that to PATH gives you psql in any terminal, which is handy for the manual-DDL migration pattern this project uses (direct ALTER TABLE + prisma migrate resolve --applied, never db push, since that wants to drop sample_sales).
