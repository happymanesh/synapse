1. Purpose and Scope

1.1 Purpose

Synapse is an internal web platform that gives SIHL staff a single sign-on entry point to several business applications, together with a reporting and data-entry engine that business users can extend without software development.

Today, adding a new report to an internal system typically requires a development cycle: specification, code change, testing, release. Synapse removes that dependency for a large class of requirements. An authorised administrator composes a report from reusable filter components and a query definition, and it becomes available to the intended users immediately.

1.2 In scope

  • Centralised authentication with password policy, login auditing and optional IP restriction.
  • A multi-application portal: one login, several products, each with its own menu structure.
  • Role-based authorisation down to individual menu options.
  • An administrator-driven reporting engine, including filters, formatting, totals, export and drill-down.
  • The same engine reused as a data-entry form for adding, editing and deleting records.
  • Internal notifications, targeted at a hierarchy level or an individual, with optional scheduling.
  • Administration screens for every master entity the platform depends on.
  • Usage analytics driving a "frequently used options" shortcut list.

1.3 Out of scope

  • Outbound email or SMS delivery. Requests are captured for follow-up; no gateway is integrated.
  • Client-facing (external) access. All users in this phase are internal.
  • Trading, order management, settlement or accounting functionality. Synapse reports on and administers data; it does not execute business transactions.
  • Migration of existing reports from legacy systems.

2. Business Context

SIHL operates across multiple business lines and a distribution network of branches, franchisees, sub-brokers and remisiers. Staff in different parts of the organisation need access to different systems and different subsets of data, governed by both the company they belong to and their position in the organisational hierarchy.

Two recurring problems motivate this platform:

  • Fragmented access. Separate logins per system create credential sprawl, inconsistent access revocation when staff move or leave, and no single view of who can reach what.
  • Reporting bottleneck. Every new report or data-capture screen competes for development capacity, so operational teams wait weeks for information they need routinely.

Synapse addresses both: one identity and authorisation model shared across applications, and a configuration-driven engine that shifts routine report creation from developers to administrators.

3. Stakeholders and User Roles

Users are classified by hierarchy, which is a distinct concept from role. Hierarchy describes who the person is within the organisation; role describes what they may do. Authorisation is evaluated against the combination of company, hierarchy and role.

5. Functional Requirements

RefRequirementPriority

FR-1.4Every login attempt, successful or failed, is recorded with timestamp, outcome, failure reason, IP address and user agent.Must

FR-1.6Sessions expire automatically after a defined period of validity.Must
FR-1.7Users may request assistance for a forgotten user ID or a password reset. These requests are captured for staff follow-up.Should
FR-1.8Administrators may reset a user's password directly.Must

6. Business Rules

These rules govern behaviour that is not self-evident from the requirements above and must be preserved in any future change.

RefRuleRationale
BR-1A user's access to an application is derived, not assigned. A user may open an application if any menu they are entitled to belongs to that application.Removes a second permission list that could contradict menu permissions. Granting a menu is sufficient and unambiguous.
BR-2A menu that is not assigned to any application is global and appears in every application. A global menu does not itself grant access to any application.Administration must remain reachable regardless of the application in use; otherwise an administrator could switch application and lose the ability to switch back.
BR-3Menu permissions are evaluated as the union of the user's active roles, restricted to the user's own company and hierarchy.The same role code may exist for several companies or hierarchies with different meaning.
BR-4Records created through a data-entry form are visible only to their creator. The restriction is enforced by the system, not by report configuration.A report author cannot accidentally expose another user's records by omitting a condition.
BR-5A scheduled notification is simply not visible before its scheduled time; no separate send action exists.Avoids a background dispatch process and the failure modes that come with it.
BR-6Usage records older than seven days are deleted. Reporting on usage never considers records outside that window.Satisfies the retention limit even if housekeeping is delayed.
BR-7Deactivating an application, or withdrawing the role that granted it, silently returns the user to their first available application at the next sign-in.A withdrawn entitlement must never leave a user unable to sign in.
BR-8Where a summary report and its detail report are intended to share filter values, both must use the same filter component. Values carry across automatically; there is no separate mapping to maintain.Keeps drill-down configuration to a single decision and prevents mismatched mappings.
BR-9Downloaded files are always named {username}_{timestamp}.Makes the origin of a shared file identifiable.

8. Assumptions, Dependencies and Constraints

8.1 Assumptions

  • All users in this phase are internal staff with organisation-issued credentials.
  • Reporting queries are authored by administrators who understand the underlying data and are trusted to do so.
  • Users have reliable network access to the internal environment.

8.2 Dependencies

  • A PostgreSQL database holding both platform configuration and the business data being reported on.
  • Company and hierarchy reference data must be populated before users can be created.
  • Any table used for data entry must carry the ownership and audit columns required by BR-4.

8.3 Constraints

  • No outbound email or SMS gateway is available; assistance requests are captured only.
  • Menu names, report titles and other administrator-authored text appear as entered and are not translated by the language setting.
  • Usage analytics cannot answer questions spanning more than seven days.

10. Glossary

TermMeaning
Application (App)One product within a company, selectable from the application switcher, with its own menu structure.
CompanyThe legal entity a user, menu, role or application belongs to.
HierarchyThe user's position in the organisation, such as Branch or Franchisee. Distinct from role.
RoleA named set of menu permissions, scoped to a company and hierarchy.
Filter componentA reusable input definition, such as "Company" or "Sale Date Range", used across many reports.
FilterA named arrangement of filter components into rows and positions.
ReportA filter bound to a query definition and display settings.
Report modeA report that runs a query and displays results.
Form modeThe same filter used to add, edit and delete records in a target table.
Drill-downOpening a related report from a value in a result row, carrying the current filter values across.
Global menuA menu not assigned to any application, therefore visible in all of them.
